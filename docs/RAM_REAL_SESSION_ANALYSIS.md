## 主要判断

用户感受到的反复探索有明确轨迹支持，但主要表现为同一类过滤行为被重复试探、误判与推翻，并非持续遍历全部目录。目录/备份路径试探集中在一次批量工具调用；模型发现相同响应后明确停止该支线。

前 6 次工具调用已经获得有效入口和关键响应。之后先转入猜测性本地破解支线，再回到主要方向，反复重写探针和响应解析代码；约第 58–60 次工具调用才稳定取得后续结构信息。会话最终声称取得答案，本分析未向平台提交或独立验证结果，不能据最终文本授予可信 Outcome。

### F1：头部截断仍丢掉有效响应，字数有界不代表内容有用

位置：`memory/ram.mjs` 的 toolLine（紧凑 110、展开 340 字符），以及 Observer 的 content_excerpt（800 字符后加截断标记）。

- 第 6 次工具调用的真实响应为 819 字符，关键成功标记约在第 471 字符。标记保留在日志 excerpt 中，但该动作在第 7–14 次请求 RAM 中的 response 只展示 110 或 340 字符，因此这些快照均没有它。
- 第 58 次工具调用的后续突破标记约在原始输出第 772 字符。脱敏展开后的文本达到采集上限，在 content_excerpt 阶段已经丢掉该标记，81 份 RAM 中也没有它。
- 这些响应包含大量 HTML/样式或重复探针结果。当前算法优先保留头部，缺少结果区域定位和差异选择。

影响边界：已证明 RAM 不包含这些有效信号；同一 Session 的完整 toolResult 仍然包含它们，因此不能将模型绕路全部归因于记忆丢失。模型当时也确实在正文识别过早期成功。

### F2：普通 shell 路径上的 RAM 实际是滚动工具流水账

事实区为空符合当前可信门：此次只有 bash/write，没有独立 Oracle 或被接受的结构化观察判断，不能将工具完成直接升格为 Fact。

问题在于另一个层次：没有持续的探索状态。助手正文中“规则已探明”“突破”等判断没有形成 proposal/claim/intent 记录；失败探针没有变成有作用域的反例；已经奏效的路径也没有保持为可追溯的观察性线索。全程 proposals/decisions 为 0，工具区只按最近性取 6 条，当前请求相关性排序未应用于工具历史。

因此当前 RAM 虽有事实/提案栏目，却缺少普通交互路径实际填充它们的闭环。修复不能绕过可信门；应持久保存有来源的观察和明确未验证的假设/计划，而非自动产生可信 Fact。

### F3：短预算被命令前缀和引用占用，判别信息比重偏低

采样请求 7、8、14、34、60、70、81：每份快照 6 条工具行中的标识、event refs、transport、分隔和其他行元信息约占 1,285–1,334 字符，另有约 925 字符的任务/标题/footer 固定部分；实际 response 片段合计约 673–890 字符。

重复的工作目录、服务地址、脚本导入和命令前缀不断占用 input 空间，真正变化的条件/结果可能位于截断后方。需要保留可追溯性，同时压缩重复元信息、区分命令骨架和参数差异，让预算更多用于观察值。

### F4：模型的实验设计与结果解释有可证实错误

- 15 次 shell 调用把已经写成百分号编码的空白序列传给再次执行 URL 编码的参数选项。离线用通用字符串验证：预编码序列会被编码成百分号自身的转义，服务端一次解码后拿到的是字面序列而非真实空白。这使模型把客户端构造问题误归因为过滤器行为。
- 18 次调用使用 shell 正则抽取结果，25 次命令涉及 SQL error 片段提取。轨迹中多次承认提取位置不对、结果为空或 probe 无效，却又在未建立完整对照时推断服务器过滤规则。
- 多次宣称规则已完全确定，随后被反例推翻；重复测试相近变体，缺少稳定的输入构造和 true/false/error 三态结果分类。

这些是具体实验设计和推理错误，不是 RAM 单独能修复的因素。改进应先验证探针自身的编码/解析和正负对照，再用其结果排除假设；不能把 malformed/error 当 false。

### F5：错误恢复增加干扰，但没有证据证明它删掉上下文

10 次模型上游错误与重试增加耗时和恢复叙述。模型后来出现“上下文有限”“上一条是否截断”等说法，但本地 context_edit 只删除空 error 消息。不能把模型的自述当成发生 Session 压缩/丢失的证据。

## 下一步修复顺序

1. **先修有界观察表示**：面向任意工具的有界 head/tail/关键差异或结果片段选择；保留脱敏、来源、截断和缺失说明。不要硬编码本题关键词，也不要只扩大预算。以长 HTML/多行输出中后部信号和脱敏膨胀为离线反例。
2. **补普通交互的探索状态闭环**：当前目标、已观察的有效路径、候选假设、支持/反例引用、探针有效性、下一判别实验和停止/切换条件。模型写入仍为未验证提案；独立验证与权限不变。保留 append-only 来源和修正，不让一次错误判断永久封死分支。
3. **让工具历史按当前问题选择**：最近观察与较早但有支撑作用的观察结合，给可重复利用的有效结果保留位置；参数和响应成对，失败只对具体条件有效。压缩重复命令/地址/标识，保持完整引用可追溯。
4. **提供探针/输出有效性反馈**：将 malformed、transport failure、解析失败与真正 negative 分开；反复无进展时先复核测试方法，再扩大候选范围。该策略要能按不同任务类型适配，不能把一套题目技巧写进 ROM。
5. **离线工程验证后再做受控真实对照**：比较重复探针率、有效线索首次发现到利用的间隔、工具调用/请求数、无进展段长度、上下文成本及独立结果。不能以这一次成功样本或合成保真用例断言改进了真实解题效率。

本轮不更改产品实现；以上是基于真实运行证据的后续修复边界，不表示已修复。原 RAM v2 的作用域、预算和临时注入保护仍成立，但之前的工程用例没有覆盖真实长 HTML/脚本输出中的判别信号，也没有证明探索策略能收敛。
