# codex

我重新看完现有设计后，判断是：

Aegis 的治理原则已经比较清楚，但“记忆模型”还没有真正成为一个可实现的数据模型。 目前文档里同时使用了 Event / Memory / Fact / Refuted / Experience / Skill / Artifact / Intent，但它们的边界、生命周期、写入权限和检索方式还没有统一，所以一落到工程实现就容易重新变成“日志 + 标签 + prompt 拼接”。

一、当前最关键的三个问题

“记忆”被分成了多个层次，但没有明确主键和关系

现在至少存在四种不同东西：
发生过什么：事件、轨迹、工具输出
当前世界是什么：Fact、指纹、条件
某种做法是否有效：Experience、Skill
下一步应该做什么：Intent、Hint、Policy

它们不能放在同一张“经验表”里。尤其是：

ok=True、一次成功、一个 Fact、一个可迁移 Skill，不是同一件事。

“机械提取”不等于“观测真实”

Observer 可以机械记录 worker 发出的：

{"tags": ["glibc2.43", "hooks_dead"]}

但这只能证明 worker 声称看到了这些标签，不能证明标签是真的。当前设计已经解决了“Observer 不让 LLM 直接写记忆”，但还没有完全解决：

谁验证结构化观测本身？

所以必须区分：
observation_claim：worker 提交的观测声明
verified_fact：Oracle 验证后的事实
derived_rule：由多个事实和结果编译出来的规则

“失败”与“证伪”仍然容易混淆

这是整个记忆系统最危险的地方：
一次失败：可能是参数错、环境错、工具坏、前置条件不满足
明确证伪：在已满足前置条件的情况下，后置条件被可靠地否定
未判定：没有足够证据

所以不能把：

尝试 Y 没成功

直接编译成：

Y 在条件 Z 下不可用

二、建议把记忆模型固定成六层

以后所有实现都围绕下面六种实体，不再继续增加同义词。

 层     名称       作用                                    谁能写
━━━━━  ━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━
 L0     Event      原始发生记录，追加不可修改              Observer
─────  ─────────  ──────────────────────────────────────  ────────────────────
 L1     Episode    一次完整任务/会话                       Runtime
─────  ─────────  ──────────────────────────────────────  ────────────────────
 L2     Claim      worker 对世界、动作或结果的声明         Worker，只能是候选
─────  ─────────  ──────────────────────────────────────  ────────────────────
 L3     Verdict    Oracle 对 Claim 的判定                  Oracle
─────  ─────────  ──────────────────────────────────────  ────────────────────
 L4     Rule       从多个 Verdict 编译出的可迁移规则       Compiler
─────  ─────────  ──────────────────────────────────────  ────────────────────
 L5     Policy     当前任务中允许、禁止或优先执行的动作    Policy 层

核心关系是：

Event
  -> Episode
  -> Claim
  -> Verdict
  -> Rule
  -> Policy
  -> 下一次 Intent

其中：

Event 是审计材料，不直接进入 prompt。
Claim 可以错，必须保留原文和来源。
Verdict 才能改变知识状态。
Rule 才能影响行为。
Policy 是当前任务的临时投影，不能反向污染长期知识。

三、建议的核心数据结构

Claim 至少包含：

claim_id
episode_id
kind: observation | action | outcome | hypothesis
subject
predicate
value
scope
source_event_ids
created_by

Verdict 至少包含：

verdict_id
claim_id
status: verified | refuted | unknown
oracle_id
evidence_tier
repro_hash
repro_count
failure_mode
checked_at

Rule 至少包含：

rule_id
when
action
expected_post
provenance_verdict_ids
positive_count
negative_count
status: candidate | active | suspended | retired
scope

这里最重要的是 scope 和 provenance：

scope 说明规则在哪个世界成立：版本、环境、设备、权限、目标类型。
provenance 说明规则由哪些判定产生，能够重放和撤销。

没有这两个字段，就会重新出现之前的“glibc 版本错一位导致经验全部失效”以及“不同会话的世界条件被拼在一起”的问题。

四、经验不是“成功动作计数”，而是条件化规则

经验的最小形式应该是：

在条件 C 成立时，
执行动作 A，
后置条件 P 以概率/计数得到结果 R。

因此不能只存：

action = tcache_dup
success = 12
failure = 3

而要存：

when:
  glibc >= 2.27
  safe_linking = false
  target = heap_allocator

do:
  tcache_dup

expect:
  arbitrary_write

evidence:
  success = 12
  failure = 3
  unknown = 4

此外，unknown 必须是正式结果，不能简单归入失败。

建议状态机：

candidate
  -> active        通过最小证据门槛
  -> suspended     出现冲突或环境变化
  -> retired       被明确证伪

失败不会直接进入 retired。只有在前置条件已验证、Oracle 明确否定后置条件时，才能进入 retired。

五、行为路径需要改成三种动作类型

当前“只有观测到的东西能驱动动作”方向正确，但表述太绝对。否则系统无法主动探索。

建议拆成：

observe：测量和确认未知状态，可以由不确定性驱动。
explore：验证候选 Intent，需要预算和失败记录。
commit：利用已验证规则执行高影响动作，必须满足前置条件。

这样可以把原则改成：

只有已观测、已验证或明确授权的状态，才能驱动非探索性动作；探索动作必须有边界和预算。

这比“所有动作都必须由已知事实驱动”更可实现，也保留了你不希望模型未雨绸缪堆代码的约束。

六、整体工程化建议

建议从一开始就使用“事件源 + 投影”结构：

append-only event log
        │
        ├── blackboard projection
        ├── episode projection
        ├── memory/rule projection
        ├── metrics projection
        └── retrieval index

推荐的模块边界：

core/
  schema.py          # Event / Claim / Verdict / Rule
  state_machine.py   # 状态迁移
eventlog/
  append.py
  replay.py
oracle/
  base.py
  deterministic.py
blackboard/
  projection.py
compiler/
  rules.py
retrieval/
  query.py
policy/
  gate.py
runtime/
  worker.py
adapters/
  pi.py
  codex.py

工程上要先保证四件事：

所有事件有唯一 event_id，写入幂等。
所有 schema 带版本号，未知版本直接拒绝。
所有派生表都可以从事件重放。
删除和遗忘只作用于投影，不删除原始审计事件。

MVP 阶段可以用：

JSONL 作为事件审计源；
SQLite 作为查询和索引投影；
文件系统保存脚本、日志、复现材料；
不先做向量数据库，不先做复杂 RAG。

七、当前文档需要先统一的地方

现有设计有几个概念冲突，继续编码前应先修正：

架构.md 说“图板是唯一真相载体”，但又说 Oracle 是唯一真值来源。
更准确的说法应该是：

图板是系统状态的唯一协调投影，Oracle 是事实判定的唯一权威来源。

README.md 的历史记录仍把“经验”描述成记忆计数，但新架构又引入了 Fact、Verdict、Rule。需要统一成新的六层模型。

docs/WP_FORMAT.md 已明确标记为历史文档，但仍然保留旧的 LLM 编译、verified 自评和 WP front matter 契约。它会继续污染设计理解，后续应该删除或重写。

“记忆不驱动行动，经验驱动行动”本质上不是两个完全不同的系统，而是：

原始记录不直接进入决策，经过 Oracle 验证和 Compiler 编译的规则才进入决策。
